# HITEL — 16개 통신 조합별 프론트 UX·라우팅 기획 v1.0

상태: **기획 / 화면 구현 이전**. 본 문서는 실제 전화 연결 및 SMS·AI 미디어 기능을 구현했다고 주장하지 않는다. 기존 운영 Fly WebRTC 서버와 기존 main 프론트는 수정하지 않는다.

## 0. 프로젝트의 핵심 제품 정의

사용자는 **전화번호·이름·대화 링크만** 선택해 연결하고, 상대방은 앱을 설치하지 않아도 된다. 사용자는 16가지 조합을 직접 선택하지 않는다. 프론트가 기기·전화망·상대방의 수신 상태를 바탕으로 연결 경로를 제시한다. 모든 통화의 동일한 기본 UI는 **통합 대화 화면 + 참가자별 비공개 AI 정보패널**이다. 통화방은 연결 수단 중 하나일 뿐 핵심 UX가 아니다.

- **P:** 일반전화만 사용하는 사람. HITEL 계정·화면 없음. 통신사 PSTN/모바일 회선.
- **P+:** 기존 휴대전화 통화(음성은 통신사 회선) 중 HITEL 네이티브 앱/웹 정보패널을 병행. 앱 설치와 통화 원음 접근은 다름.
- **N:** HITEL 네이티브 앱에서 인터넷 오디오/비디오에 참여. 앱은 시스템 연동 엔진이고 화면은 같은 Vite 웹.
- **W:** 모바일·PC 브라우저에서 HITEL 웹 WebRTC에 참여. 앱 불필요.

상대방이 P이면 상대방에게 HITEL UI 또는 개인 AI가 생겼다고 표시하지 않는다. P→P처럼 양쪽 모두 HITEL을 사용하지 않는 순수 통신사 전화는 HITEL 연결/화면이 없다. HITEL 사업자가 관리하는 별도 PSTN 브리지로 통화가 통과하는 특수 유형은 별도 관리자 UI를 정의한다.

## 1. 사용자에게 보이는 진입점: 16개의 버튼이 아니라 네 가지 행동

1. **연락하기:** 사람/기관 검색, 연락처, 번호 010/120, 최근 기록 선택. 연결 가능한 방법을 바로 제시.
2. **걸기:** 음성 / 영상 / 문자·수어 선택. 자동으로 HITEL 연결이 가능하면 먼저 표시하고, 일반전화 연결을 선택할 수 있다. 요금과 발신번호 표시는 실제 통신 정책에만 근거.
3. **받기:** W/N은 HITEL 수신화면; P+는 기본 전화 앱이 수신하고 HITEL 화면에는 '현재 통화 AI 도우미 열기'를 제공. P는 HITEL 화면 없음.
4. **통화 중 도우미 열기:** 현재 이용 가능한 STT·번역·수어·TTS·지식패널을 활성화. 음성 접근이 없는 상황에서 자동 STT 또는 상대방 전달 TTS 버튼을 표시하지 않는다.

직접 연결 수단을 바꾸는 '연결 변경' 고급메뉴는 통화 중에도 제공. 기존 PSTN 통화가 WebRTC로 **자동** 전환된다고 표시하지 않는다.

## 2. 16개 전체 조합 (발신 → 수신)

| ID | 발신 → 수신 | 발신 화면 / 초기 행동 | 수신 화면 / 초기 행동 | 실제 미디어 경로 | 개인 AI와 주요 UI |
|---|---|---|---|---|---|
| 01 | P → P | 없음 | 없음 | 기존 PSTN 직접 | HITEL 비참여. 게이트웨이가 실제 경유하는 경우에만 관리자형 세션 |
| 02 | P → P+ | 없음, 일반 010 발신 | 기본 전화 수신 + HITEL 도우미 패널 | PSTN 직접 | 수신자의 비공개 AI; 음성 미디어 기능은 기기 능력에 따름 |
| 03 | P → N | 기존 010 또는 HITEL 대표번호로 일반 발신 | 앱 푸시/수신 → HITEL 통화 화면 | PSTN/DID/착신전환 → gateway → N 인터넷 음성 | 수신자 AI, 발신자 앱 없음 |
| 04 | P → W | 일반전화 발신 | 온라인 웹 수신 팝업 → 웹 통화 | PSTN/DID → gateway → W WebRTC | 웹 수신자 AI. 브라우저 미접속 시 대체수신 정책 |
| 05 | P+ → P | HITEL 웹에서 번호 검색 → 네이티브 시스템 전화 열기 → 도우미 | 없음, 일반전화 수신 | PSTN 직접 | 발신자 AI. 기존 이동통신 통화 원음 자동 분석은 별도 능력 |
| 06 | P+ → P+ | 기존 010 발신 + 도우미 | 일반 010 수신 + 도우미 | PSTN 직접 + 두 HITEL 데이터 세션 | 양측 각각 비공개 AI. 상호 페어링은 명시적 승인 후 진행 |
| 07 | P+ → N | 기존 휴대전화 발신 + 도우미 | 앱 수신 → 응답 | PSTN/DID → gateway → N | 발신/수신 양쪽 AI(각자 앱 이용 시) |
| 08 | P+ → W | 기존 휴대전화 발신 + 도우미 | 온라인 웹 수신 → 응답 | PSTN/DID → gateway → W | 발신/수신 각각 AI |
| 09 | N → P | 앱 통화 화면에서 일반전화번호 선택 → 연결 요청 | 일반전화 수신 | N 인터넷 음성 → gateway → PSTN | 앱 발신자 AI, 상대 설치 불필요 |
| 10 | N → P+ | 앱 인터넷전화 발신 | 기본 전화 수신 + HITEL 도우미 | N → gateway → PSTN | 양측 각자 AI (상대 앱 데이터 세션 별도) |
| 11 | N → N | 앱 연락처 검색 → 인터넷통화 요청 | 앱 푸시/수신 | 기존 WebRTC 미디어 연결 | 양측 독립 AI, 영상/수어/자막 |
| 12 | N → W | 앱에서 사용자/링크로 통화 요청 | 웹에서 수신 | 기존 WebRTC 미디어 연결 | 양측 독립 AI, 영상/자막/자료 |
| 13 | W → P | 웹 다이얼패드에서 번호 입력 | 일반전화 수신 | W WebRTC → gateway → PSTN | 웹 발신자 AI |
| 14 | W → P+ | 웹 다이얼패드 발신 | 일반전화 수신 + HITEL 도우미 | W → gateway → PSTN | 양측 각각 AI |
| 15 | W → N | 브라우저에서 사용자/초대 링크로 호출 | 앱 푸시/수신 | 기존 WebRTC 미디어 연결 | 양측 각각 AI |
| 16 | W → W | 브라우저 링크·ID로 호출 | 웹에서 수신/링크 승인 | 기존 WebRTC 미디어 연결 | 양측 각각 AI |

*P→N/W·P+→N/W는 상대의 010 번호만 안다고 인터넷 수신이 일어나지 않는다. 해당 번호의 통신사 착신전환→DID 라우팅 또는 별도 공개 HITEL 번호가 설정되어야 한다. 목적지가 '120'처럼 특수번호이면 해당 PSTN 사업자의 단축번호 라우팅을 검증하고, 지원하지 않는 경로를 호출하지 않는다.*

## 3. 프론트에서 사용하는 라우팅 결정

**입력:**
- \`originParticipant\`: 발신 이용자의 계정·기기 능력·선택한 호출 모드
- \`destination\`: 전화번호/회원 ID/초대 URL/대표번호
- \`destinationPresence\`: HITEL 계정 유무 및 online 앱/웹 상태(공개 동의 범위)
- \`forwardingBinding\`: 연결 가능한 DID/착신전환 설정 및 검증 결과
- \`mediaCapabilities\`: 오디오 읽기/쓰기/영상/마이크/카메라/네이티브 TTS/통화 주입/통역 모드
- \`purpose\`: 일반, 과외, 의료, 부동산, 공공서비스 등 AI 패널의 도메인

**라우터 결과:** \`scenarioId\`, \`originChannel\`, \`destinationChannel\`, \`mediaLegPlan[]\`, \`inviteMode\`, \`uiMode\`, \`supportedActions[]\`, \`disabledReasons{}\`, \`billingDisclosure\`, \`fallback[]\`.

라우터는 반드시 FastAPI가 통화 인가·번호·라우팅 가능 여부를 최종 판정해야 하며 프론트의 판단은 UI 프리뷰용이다. \`P+\`의 일반통화 발신은 \`tel:\` 또는 기본 전화 앱 열기이지, HITEL 음성 연결 성공이 아니다. AI 송출 대상은 \`local_only\`, \`remote_party\`, \`both\` 등으로 명시적으로 구분한다.

## 4. 화면 라우트

| 라우트 | 화면 | 주 기능 |
|---|---|---|
| \`/portal\` | 홈 | 대화 검색, 최근기록, '전화 걸기' '내게 걸려온 전화' 'AI 상담' |
| \`/portal/dial\` | 통합 발신기 | 전화번호/ID/초대 링크 입력, 추천 경로, 요금·신뢰 표시 |
| \`/portal/incoming/:interactionId\` | 수신 | 발신자, PSTN/WebRTC 구분, 받기/거절/오디오·영상 선택 |
| \`/portal/call/:interactionId\` | 통합 통화 워크스페이스 | 오디오/영상 영역 + 대화 타임라인 + 나만의 AI 패널 |
| \`/portal/invite/:token\` | 비회원 초대 | 브라우저 입장 전 동의·장치 확인 |
| \`/portal/contacts\` | 주소록/상담 채널 | 개인, 전문상담자, 업체, 공공기관 |
| \`/portal/history\` | 최근 통화 | 발신·수신 내역, AI 생성 결과물 |
| \`/portal/settings/phone\` | 전화 연동 | 번호 인증, DID, 착신전환 상태 |
| \`/portal/settings/devices\` | 기기 연동 | 앱·브라우저 기기, 연결 상태 및 시스템 기능 |
| \`/portal/flows\` | 개발용 16가지 시나리오 기획 화면 | 4×4 매트릭스, 발신/수신 UI·미디어/AI 동선 확인 |

모바일 앱 WebView와 직접 모바일 브라우저가 **동일한 React 화면**을 연다. 시스템 통화 기능만 NativeBridge/서버 어댑터로 호출한다. 푸시 클릭은 동일한 \`interactionId\`를 연다.

## 5. 통화 워크스페이스 (단 하나의 컴포넌트)

### 헤더
상대방 명칭·번호·검증 상태·통화 종류(일반전화/인터넷전화)·마이크 경로·경과시간·참가자 수.

### 통화 영역
- P/P+: 기본 전화의 시스템 UI를 복제하지 않는다. 별도 AI 도우미 오버레이/웹 화면. 지원되지 않는 '원격 마이크 끄기' 등은 미노출.
- N/W: 실제 WebRTC 영상/오디오 타일 및 음성·카메라 제어. 전화망 참가자는 영상 없는 전화 아이콘 타일로 표시.
- 그룹: 전화 참가자·웹 참가자·통역사·AI 발언자를 참가자 타일로 표시하고 권한별로 제어.

### AI 개인 영역 (비공개 기본값)
'실시간 자막' / '번역' / '수어 입력' / '문자로 말하기' / '내 AI에 질문' / '전문 자료' / '메모' 탭. 원문·번역문의 화자 구분 및 비공개/상대방 발송 상태 표시.

### 합성음성 UX
'내 스피커로 듣기'와 '상대방 전화로 전달'은 **다른 액션**. \`remote_party\`는 미디어 송신 경로가 실제 구성된 경우에만 활성화. 음성 입력/수어 입력 후 번역문은 사용자가 확인·수정하고 전송할 수 있게 한다.

### 반응형
휴대전화에서는 하단 통화 제어 막대 고정, 상단 상대방/연결 상태, 중앙 대화(영상 옵션), '내 AI' 패널은 아래 슬라이드업. 태블릿/PC에서는 대화 왼쪽, 개인 AI 오른쪽 분할. '나만의 AI'는 다른 사람에게 화면 공유되지 않으며 명시적 공유 기능만 별도 허용.

## 6. 화면 상태머신

\`IDLE → RESOLVING → [INVITING | PSTN_DIALING | RINGING] → CONNECTING → ACTIVE → [HOLD | ADD_PARTICIPANT | HANDOFF] → ENDING → ENDED\`

오류: \`NO_ROUTE\`, \`NO_PERMISSION\`, \`OFFLINE\`, \`GATEWAY_UNAVAILABLE\`, \`MEDIA_UNAVAILABLE\`, \`REJECTED\`, \`TIMEOUT\`, \`CONNECTION_LOST\` 별 사용자 복구 화면. 네트워크 재접속 시에도 \`interactionId\` 유지. 통화가 종료되면 원치 않는 재접속을 하지 않는다.

| 상황 | 실제 프론트 처리 |
|---|---|
| 상대 W 오프라인 | 통화 중인 것처럼 보이지 않고 초대 링크 또는 재시도 선택 |
| 상대 N 백그라운드 | 푸시 수신·수락 후 세션 결합 (통화 수락은 OS 연동) |
| 상대 P+의 기존 010 수신 | 시스템 전화가 울리고, HITEL 화면은 별도 AI 연결 상태로 전환 |
| P+ 일반통화 감지 불가 | 이용자 '진행 중인 전화에 AI 도우미 연결'을 직접 실행 |
| 한쪽 원음 접근 불가 | 원문 자동 자막·원격 TTS 삽입을 미지원 표시; 텍스트·정보패널 사용 가능 |
| 통화방 → 일반전화 참가자 추가 | 별도 gateway leg 추가 필요, 기존 Fly 세션을 임의 변형하지 않음 |
| WebRTC로 핸드오프 | 새 연결을 수립하고 성공 확인 후 기존 연결 종료; PSTN이 자동 변환됐다고 표시하지 않음 |

## 7. 실제 이용 사례를 표준 화면 위에 매핑

- **120 공공상담**: 상대방은 P. HITEL 이용자는 P+/N/W 중 하나. P+는 네이티브 일반전화 + AI 패널, N/W는 게이트웨이 통한 전화 연결. 수어·번역 TTS는 실제 상대방 송출 경로가 가능한 모드에서만 '보내기'.
- **부동산 중개인**: 고객 P→중개인 P+이면 기존 010 수신 옆 개인 매물 패널; P→N/W이면 DID 연동 수신 후 매물 패널. 기존 010을 등록했다는 사실만으로 DID가 생기지 않음.
- **과외**: 선생님 W↔학생 N/W 또는 P/P+. 양쪽 각각 독립된 AI 패널과 독립 비공개 지식검색. 학생이 P인 경우 학생의 AI 화면은 없음.
- **수어 이용자**: 영상 카메라 기반 수어→검수 문장→상대방에 문자/WebRTC TTS/PSTN TTS. 상대방 음성→자막은 오디오 수신 가능한 경로에서만 활성.

## 8. 화면 전환·참가자별 데이터 권한

각 화면은 \`InteractionViewModel\`에만 의존한다.

- \`interactionId\`, \`status\`, \`purpose\`
- \`localParticipant\`/\`remoteParticipants\`: \`userId?\`, \`displayName\`, \`mediaChannel\`, \`role\`
- \`legs[]\`: \`native_cellular\`, \`pstn\`, \`webrtc\`, \`data_sidecar\`
- \`capabilities[]\`, \`permissions[]\`: readLocal/readRemote/injectRemote/translate/sign/webcam 등
- \`aiSessions[]\`의 \`ownerParticipantId\`와 개인별 scope
- \`transcriptEvents[]\`: \`sourceParticipantId\`, \`visibility\`, \`language\`, \`deliveryTarget\`
- \`routingReason\`과 \`fallbackOptions\`

원문/번역문 저장과 상대방 공유는 동의·권한에 따라 구분하며 공용 상태저장소에 개인 AI 지식/기억을 통째로 넣지 않는다.

## 9. 프론트 개발 순서

1. **16시나리오 Catalog + Flow Resolver의 순수 타입/데이터**. 각 셀의 역할·미디어·AI를 표로 검증.
2. **통합 홈·연락처·발신기**. 16개 케이스를 버튼으로 나열하지 않고 전화번호/상대방 검색 중심으로 자동 경로 선택.
3. **수신·초대 UX**. P+ 측면패널 / N 앱 푸시 / W 웹 수신의 UI 동작을 분기.
4. **통합 통화 워크스페이스**. 미디어 상황별 제어, 개인 AI 탭, 수어/번역 문자 검수.
5. **실제 Interaction Router API와 이벤트 연결**. 서버의 capability 응답으로 UI 액션 활성.
6. **WebRTC 경로 실제 연결**, PSTN·기존 010·통신사 연동은 선택된 미디어 어댑터별로 구현.

16개 행별로 **발신/수신 화면, UI 상태변화, AI 개인정보 격리, 미지원 기능 비활성화**를 프론트 테스트한다. 기획화면의 '연결 시뮬레이션'은 UI 검증일 뿐 PSTN 또는 실제 WebRTC 통화로 보고하지 않는다.

## 10. 기존 코드에서 바꿀 사항

현재 \`src/portal/Portal.tsx\`의 4개 연결방식 버튼은 **테스트/설정 중심 화면**이다. 최종 홈은 일반 이용자가 16개 모드를 모른다는 전제에서 다시 구성한다. \`services/hitel-api/app/main.py\`의 현재 Interaction은 \`channel\` 하나와 \`target\`만 저장한다. 이는 양쪽 Media Leg, 멀티디바이스, 양측 AI를 충분히 표현하지 못한다. 최종적으로 \`origin/destination\`, \`participants\`, \`legs\`, \`capabilities\`, \`events\`로 확장해야 하며 **프론트 기획이 확정될 때까지 API/미디어 서버 변경은 하지 않는다**.

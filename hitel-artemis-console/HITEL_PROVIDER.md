# ARTEMIS — original HITEL Universal AI API client only

Original repository: https://github.com/lyonbegin/hitel-scribd-runner/tree/feature/hitel-universal-ai-ui-api-20261127

Original API guide: https://github.com/lyonbegin/hitel-scribd-runner/blob/feature/hitel-universal-ai-ui-api-20261127/docs/HITEL_UNIVERSAL_AI_PUBLIC_API_GUIDE_KO.md

ARTEMIS sends requests exclusively through the documented GitHub Contents/Actions endpoints on the original repository. No copied engine, watchdog, separate backend, direct relay calls, or local approval flags. The original repository source is not modified by this client.

The documented input is a new project JSON with provider=hitel and an already approved dedicated task_id; result is original state.json and results.csv, with events.json used for progress. The original workflow owns execution and approval. Do not reuse an unrelated task. The existing authorized GitHub connection is required for writes; runtime GH_TOKEN follows the original API guide. The GitHub Actions repository-scoped default token cannot be assumed to write to another repository. No browser token field, no OpenAI/Gemini key. This public target accepts only public synthetic data. Actual AI execution remains unverified until the original API returns a verified response. Push runs test the client and read existing public mock evidence only.

## Review corrections
The client validates task ID syntax and GitHub transport only; it does not approve live work. The original engine and server own authorization. A project rejection can precede state.json creation; inspect the original workflow job log for the exact PROJECT_REJECTED project ID. A missing state alone is not failure or success. The workflow has a stable request_id input, independent of GITHUB_RUN_ID, and model tool call IDs are deterministic. Resume the identical goal and request_id to reuse the same per-turn projects. The default per-turn wait is 1200 seconds; on expiry the original project is pending, never automatically re-registered. Read an existing project independently with python hitel_transport.py PROJECT_ID --run-id ORIGINAL_RUN_ID (optional GH_TOKEN for authorized log reads); it performs GET only. A new project may dispatch once after two missing-run checks; an uncertain dispatch is reconciled by lookup, not repeated. The output directory is explicit. The external GitHub credential is distinct from original OIDC; current connector rights do not automatically propagate to Actions. No token is supplied in the repository or browser. The original repo remains unchanged by these corrections. Actual live task approval and real end-to-end AI are not proven by fixture tests.

## Connector-first handoff (default)

`ARTEMIS_API_MODE=connector` is the default. In this mode the existing consumer creates an exact project JSON under `console-results/connector-projects/<project_id>.json` and only reads the original API. It requires the original operator-approved `task_id` and stable request ID, but no runner write token. Missing project/state is reported as unconfirmed/pending, not as approval or success. The approved GitHub connector/operator must separately review the public synthetic project JSON, verify live authorization, and register it via the original documented API. Do not register or dispatch if the original approval/access is absent. Resume the identical request to consume the existing result; the client verifies original project and checkpoint definition hashes, live provider, record identity and CSV equality. Runtime submission remains explicitly selectable (`ARTEMIS_API_MODE=runtime`) only with authorized credentials and the original approval. No new workflow, server, Task or original API modification is required for this client handoff. The existing consumer workflow's push tests remain offline/read-only; its optional manual run defaults to connector mode. An initial direct API test can be carried out independently by the approved connector after the original operator has approved it, without launching this consumer workflow.
